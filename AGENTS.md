# Reports module

Drupal contrib module `reports`: plugin-based site reports, shown as DataTables tables or like core's status report, downloadable as CSV or Excel, and runnable with Drush. See `README.md` for features and the plugin API.

## Architecture

- Plugins: `src/Plugin/Report`, `#[Report]` attribute (`src/Attribute/Report.php`), managed by `ReportManager`.
  - `RealtimeReportInterface` builds rows on every request (`getRows()`).
  - `GeneratedReportInterface` builds them with the Batch API (`getBatchOperations()`): each operation is a public plugin method called with its arguments, a `ReportWriter` and `&$context`.
  - `ReportBase` is the base class; `EntityReportBase` (experimental, `@internal`) adds the `include` option (unpublished, trashed), entity queries and batches, and the entity columns from Helper's `EntityHelper::toArray()`; `FormattedTextReportBase` (experimental, on `EntityReportBase`) scans formatted text fields and custom field subfields for reports like HTML elements; `LinkReportBase` (experimental, on `FormattedTextReportBase`) also scans link and URI fields and subfields, for reports like Absolute URLs; `StatusReportBase` is for `type: 'status'` reports.
- Sheets: `getSheets()` returns labels keyed by sheet ID (`ReportInterface::SHEET_DEFAULT` for single-sheet reports, or class constants for others), and `getHeader($sheet)` each sheet's columns. Columns are labels or arrays with `label`, `filter` (`list`, `search` or FALSE), `url` (column key to link to) and `hidden`.
- `ReportStorage` keeps generated files in `getDirectory()` (`$settings['reports_directory']`, default `private://reports`; public and temporary directories get a warning), named `<key>.csv`, `<key>.<sheet>.csv` and `<key>.xlsx`, where the key is the plugin ID plus an HMAC of the plugin ID and options, keyed with the site's hash salt and private key, so file names can't be guessed. Keys never contain a dot. Status is in the `reports` key/value collection.
- `isApplicable()` is static (like core's formatter and widget `isApplicable()`), takes the plugin definition and uses `\Drupal::` for services; call it through `ReportManager::isApplicable($id)`. It hides a report's menu link and makes its pages 404 when it doesn't apply (e.g. an optional module isn't installed); `getRequirements()` explains fixable problems. `ReportManager::getRequirements()`/`isUsable()` add the storage requirement for generated reports; pages, generate access, the options form and Drush use them. The status report only shows `getGlobalRequirements()` (storage and route conflicts).
- Generating is guarded by the status, not core's persistent lock (whose locks share one owner and can't be extended in later requests): `ReportStorage::start()` refuses with `ReportGeneratingException` while a generation of the same key is running, i.e. its `heartbeat` (updated by each batch operation) is under `GENERATING_TIMEOUT` (5 minutes) old. A short regular lock makes the check-and-set atomic.
- Download-only reports (`downloadOnly: TRUE`) keep only their Excel file; their sheet row counts are stored in the status.
- Reports are at `/admin/reports/{plugin ID}`. `Routing\ReportParamConverter` (route option `type: report`) turns `{report}` into the plugin, with options from the `config` query string, and returns 404 for unknown reports and ones that don't apply; access callbacks and controller methods receive the plugin. Build report URLs with the report's `toUrl($rel, $options)` (`canonical`, `csv`, `xlsx`, `generate`), which adds its configuration to the query string, rather than `Url::fromRoute('reports.report…')`. Menu links under Reports from `Plugin/Derivative/ReportMenuLinks`. Report IDs must not match other routes' paths under `/admin/reports` (e.g. `status`, `dblog`): those routes win. `ReportManager::getConflictingRoute()` detects it; such reports get a status report warning (`getGlobalRequirements()`) and no menu link. Reports can instead replace other modules' routes (`routes` in the attribute, route name => sheet): `Routing\ReportRouteSubscriber` gives those routes the report page's controller, keeping only their own access requirements, which `ReportBase::access()` also uses (so downloads match the page), and `ReportManager::getReplacedRoutes()` lists the ones that exist; those reports use the routes' menu links and local tasks instead of their own link and sheet tabs.
- DataTables code is kept generic, to move to the datatables module later (plan in the local notes): the `DataTables` and `drupal.datatables*` libraries in `reports.libraries.yml`, `js/datatables*.js`, `css/datatables*.css` and `Hook/DataTablesHooks.php` must not depend on reports code. `js/datatables.js` (library `reports/drupal.datatables`) starts DataTables on `table[data-datatables]` (`data-datatables-page-length`) and dispatches a bubbling `datatables:init` event with `detail.dataTable`; add-ons listen for it and add to `detail`, so scripts reading an add-on's detail must depend on its library (listeners run in the order added). `js/datatables.exposed-form.js` (`reports/drupal.datatables.exposedForm`, not a dependency of `drupal.datatables`: attach it with the attribute) listens for `datatables:init` and sets `detail.exposedForm` for tables with `data-datatables-exposed-form` (`-autosubmit` to filter as fields change), from column headings with `data-datatables-exposed-filter="list|search"`; `DataTablesHooks::libraryInfoAlter()` adds `views/views.module` so admin themes style it. `js/reports.js` listens for `datatables:init` on `.reports-table` to add the filtered download button.

## Conventions

- Batch callbacks declare the context untyped (`&$context`), with `@param array|\ArrayAccess $context`.
- `getSummary()` describes what the report checks, never its current options: don't read `$this->configuration` in it (2026-10-26: HTML elements' summary showed an empty selector before the report was run). The options form shows the options.
- Plugins validate their configuration in `setConfiguration()`: it comes from the query string and Drush options. Store list options as comma-separated strings with `ReportBase::normalizeList()` (which also sorts them, so equivalent options get the same storage key) and read them with `getListOption()`: the query string drops empty arrays, so an emptied list would fall back to its default.
- Don't add `?destination=` to URLs that reports list, such as edit or delete links. Only add one when the target needs it to work, e.g. core's file delete form, which crashes without a destination when files have no canonical page (`UnusedFiles::processFiles()`).
- Use list cache tags (bundle list tags, config list tags) in `getCacheTags()`, not individual entity tags.
- Prefer Helper's APIs (`EntityHelper`, `EntityType`, `ArrayHelper`, `TrashHelperTrait`). Code that should move to Helper gets a `@todo` and a task in Helper's local notes.
- Code must work on Drupal 11.3 (`core_version_requirement: ^11.3`), e.g. `FilterFormat::getRoles()` is 11.4 only.

## Tests

- Run checks with the ddev-drupal-contrib commands from the module root: `ddev phpunit tests/src/Kernel` (the path must come first, so the command adds core's test bootstrap; `ddev exec vendor/bin/phpunit` fails with "Class KernelTestBase not found"), `ddev phpstan`, `ddev phpcs` and `ddev eslint`. They test against the core version the module's Composer setup installs (11.4 as of 2026-10-26), while `core_version_requirement` allows ^11.3: check 11.3 separately, e.g. drupal.org CI's previous-minor job.
- Kernel tests in `tests/src/Kernel`, test plugins in `tests/modules/reports_test`.
- `GeneratedReportTest` sets `file_private_path` in `setUpFilesystem()` (the private stream wrapper must exist before the kernel boots), and installs every `entity_test*` entity type with link or text fields, since Absolute URLs scans all content entity types.
- Read download-only reports' data from their Excel file (`readSpreadsheet()`), since their CSVs are deleted.
